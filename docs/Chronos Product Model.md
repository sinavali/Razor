# Chronos Product Model – v1.0.0 LTS

## 1. Product Overview

Chronos is an institutional‑grade algorithmic trading engine designed for **strategy optimisation and fully managed automated trading**. It is delivered as a distributed ecosystem where a lightweight, headless execution engine runs on the client’s own infrastructure, while all control, scheduling, monitoring, reporting, and plugin management is centralised in a cloud‑based control plane.

The product consists of four components:

- **Chronos Engine** – the execution node deployed on client servers.
- **Chronos Cloud** – the central management, command, and reporting dashboard.
- **Chronos Marketplace** – a separate service for discovering and distributing plugins (adapters, strategies, etc.).
- **Chronos Abstractions** – a public SDK exposing only the contracts needed for plugin development.

This model ensures clients retain full custody of their funds and trading infrastructure while receiving an enterprise‑grade toolset for strategy development, optimisation, and live execution—all managed through a rich web interface.

## 2. Product Components

### 2.1 Chronos Engine

The Engine is a single, headless binary that serves both developers and production users. There is no separate “DevEngine” build. The same executable is deployed everywhere, with capabilities gated entirely by the license and permissions issued by Chronos Cloud after authentication.

**Key characteristics:**

- **Headless operation** – After authentication, the Engine displays a live log stream and writes rotating daily log files to a local `logs/` directory. It provides no interactive CLI, menu, or local command interface. All interactions happen through Chronos Cloud.
- **Stateless execution node** – The Engine holds no long‑term configuration, schedule, or business logic. It receives commands (run backtest, start live, inject genes, etc.) along with all required configuration from the Cloud, executes them, and streams results back. The Cloud is the single source of truth.
- **Task‑oriented architecture** – From v2.0.0 LTS, the Engine will support concurrent operations (e.g., running a live trading session while executing an optimisation). Each operation is isolated with its own clock, broker instance, and data context.
- **Platform support** – Windows (x64) and Linux (Debian/Ubuntu, x64).

**Bootstrap configuration** – The Engine requires only a minimal local file containing the Cloud endpoint, instance API key, and encryption seed. All operational parameters (strategy specs, execution specs, timeframes, symbols, etc.) are pushed from the Cloud per command.

### 2.2 Chronos Cloud

Chronos Cloud is the web‑based control plane and dashboard. It is the **sole interface** through which users interact with their engines, regardless of whether they are developing a strategy or running a live production instance.

**Capabilities:**

- **Instance management** – Register engines, issue and revoke API keys, monitor connectivity and health.
- **Remote command & control** – Start/stop strategies, trigger backtests, launch optimisations, inject genes, deploy plugin DLLs, update engine binaries. All commands are queued and executed when the engine acknowledges.
- **Scheduling** – The Cloud holds all scheduling logic. For example, continuous optimisation runs are triggered by the Cloud based on user‑defined calendars; the engine has no timers for operational decisions.
- **Real‑time monitoring** – Live equity curves, open positions, pending orders, margin utilisation, connection status, and tick freshness.
- **Reporting & analytics** – All backtest and optimisation results are stored in the Cloud. Users generate rich reports (equity curves, metrics, trade lists, population histories) on demand or on schedule. Reports are never generated by the engine itself; the engine ships raw result data, and the Cloud renders it.
- **User & license management** – Role‑based access, subscription tracking, feature flags, instance limits.
- **Configuration management** – All strategy, execution, and optimisation configurations are created and stored in the Cloud. The engine holds no local configuration beyond the bootstrap.
- **Secrets management** – Users can store broker API keys and other secrets in the Cloud; the engine fetches them when needed via the encrypted channel.
- **Plugin deployment** – Users upload or select plugins from the Marketplace, and the Cloud pushes signed DLLs to the engine.

**Deployment** – Chronos Cloud is a SaaS application hosted by Chronos Co. It is not self‑hosted by clients.

### 2.3 Chronos Marketplace

The Marketplace is a separate service, distinct from Chronos Cloud, that handles the discovery, distribution, and monetisation of plugins (adapters, strategies, indicators, etc.). It shares the same user identity system as Chronos Cloud and communicates with the Cloud through secure internal APIs.

**Capabilities:**

- **Plugin catalog** – Listings for free and paid plugins, including community‑developed and Chronos‑curated items.
- **Licensing** – Respects the user’s Cloud subscription and permissions. Purchases are linked to the user account.
- **Version management** – Tracks plugin versions, declares compatibility with Chronos SDK versions, and supports updates.
- **Distribution** – When a user acquires a plugin, the Marketplace notifies Chronos Cloud, which then handles deployment to the relevant engine instances.

**Monetisation** – Chronos Co. charges a transaction fee on each sale occurring on the Marketplace.

### 2.4 Chronos Abstractions (Public SDK)

To enable plugin development without exposing engine internals, Chronos Co. publishes a **public NuGet package** (`Chronos.Abstractions`). This package contains only the interfaces, abstract base classes, and data models required to compile an adapter or strategy. It includes no runtime implementations, no broker logic, no GA engine, and no pipeline code.

The package is proprietary but freely redistributable. It may be open‑sourced at a later stage.

## 3. Deployment & Distribution

### 3.1 Engine Distribution
The Engine binary is distributed as a compressed archive for Windows and Linux. It is fully obfuscated and protected against reverse engineering (see Section 6). Updates are triggered remotely by Chronos Cloud; the engine downloads the new binary, verifies its integrity, and restarts.

### 3.2 Client Responsibilities
The client must:

- Provision a server (physical, virtual, or cloud) meeting minimum specifications.
- Install the Engine binary.
- Ensure outbound network access to Chronos Cloud and any required broker APIs.
- Manage server‑level security (firewall, OS patches).

### 3.3 Plugin Development Environment
Plugin developers:

- Install the `Chronos.Abstractions` NuGet package in their .NET project.
- Compile their plugin DLL against the SDK interfaces.
- Test locally by running the Chronos Engine in their development environment. The same engine binary is used; a free development license from Chronos Cloud limits capabilities (e.g., only a mock adapter for live testing, limited historical data range).
- Deploy plugins by uploading them to Chronos Cloud (which then pushes to the engine) or, during local testing, by placing the DLL in a designated folder.

## 4. Licensing & Subscriptions

### 4.1 Subscription Tiers
Chronos is sold as a per‑user subscription with the following durations: 4 months, 6 months, 12 months. Each subscription includes one engine instance by default. Additional instances can be purchased incrementally.

A **free development tier** is available. It provides full access to Chronos Cloud and the Engine, but with functional limitations enforced by the license key:

- Only a mock adapter for live trading (records all sent orders without execution).
- Historical data limited to a predefined rolling window (e.g., 3 months).
- All other features (backtesting, optimisation, reporting) are fully functional.

### 4.2 Feature Gates
Capabilities are enforced by the Cloud through a signed capability set transmitted to the engine after authentication. The engine enforces these capabilities locally; any attempt to bypass them is reported to the Cloud.

### 4.3 Instance API Keys
Each engine instance is registered in Chronos Cloud and assigned a unique API key. This key is used during the initial WebSocket handshake to authenticate the instance. Users create and revoke keys from the Cloud dashboard.

## 5. User Workflows

### 5.1 Developer Workflow
1. Register for a free developer account on Chronos Cloud.
2. Download the Chronos Engine binary.
3. Install the `Chronos.Abstractions` NuGet package.
4. Develop a strategy or adapter locally.
5. Run the engine with the development license key; it connects to Chronos Cloud.
6. Use the Cloud web interface to upload the plugin, configure a backtest, and view results.
7. Iterate until the strategy is ready.
8. Upgrade to a paid subscription, replace the mock adapter with a real broker adapter, and deploy the same engine binary on a production server.

### 5.2 Production Workflow
1. Purchase a paid subscription.
2. Deploy the Engine on a production server with the production license key.
3. From Chronos Cloud, configure the live trading session, upload the production adapter, and start the strategy.
4. Monitor real‑time performance, receive alerts, and periodically run optimisations—all from the Cloud dashboard.
5. When the Cloud schedules an optimisation, it sends a command to the engine; results are reported back and displayed, and upon user approval (or automatic timeout), the Cloud pushes new genes to the live engine.

## 6. Communication & Security

### 6.1 Engine–Cloud Channel
The Engine maintains a persistent, encrypted WebSocket connection to Chronos Cloud. Because client servers may not have TLS certificates, a custom end‑to‑end encryption layer is used:

- Session establishment: ECDH key exchange authenticated with the instance API key.
- Data encryption: AES‑256‑GCM with per‑message authentication tags and sequence numbers to prevent replay attacks.
- All traffic is encrypted, including binary payloads (tick data, result files, logs).

### 6.2 Engine Binary Protection
The Chronos Engine is the sole container of all trading logic and must be protected against reverse engineering, tampering, and cracking.

- **Obfuscation**: Symbol renaming, control flow obfuscation, string encryption. Integrated into the CI/CD pipeline.
- **Integrity verification**: The Cloud may issue periodic challenges requiring the engine to compute a hash of its in‑memory image. Mismatches lead to instance suspension.
- **Anti‑debugging**: Runtime checks for attached debuggers; engine refuses to start if a debugger is detected.
- **Encrypted configuration**: Local bootstrap file is encrypted at rest.

### 6.3 User Secrets
Broker API keys and other secrets are stored in Chronos Cloud. The engine retrieves them over the encrypted channel when needed. A local encrypted secrets file may be used as a cache but is not the primary store.

### 6.4 Marketplace–Cloud Communication
Chronos Marketplace and Chronos Cloud communicate via secure internal APIs with mutual authentication (client credentials or shared secrets). User data is shared only to the extent necessary for licensing and plugin delivery.

## 7. Configuration Management

- The Engine’s local configuration file is limited to: Cloud endpoint URL, instance API key, encryption parameters, and log verbosity.
- All operational configurations (strategy specifications, execution parameters, optimisation settings, live trading parameters) are created and stored in Chronos Cloud.
- When the Cloud sends a command (e.g., `RunBacktest`), the full configuration is included in the payload.
- Users modify configurations through the Cloud web interface; changes take effect immediately or on the next operation, depending on context.
- Chronos Cloud is the immutable source of truth for all configurations; any local state on the engine is temporary and disposable.

## 8. Control & Monitoring

### 8.1 Command Model
Chronos Cloud issues asynchronous commands to the Engine. Each command has a unique ID, a type, and a payload. Example commands:

- `StartLive` / `StopLive`
- `RunBacktest`
- `StartOptimization` / `CancelOptimization`
- `InjectGenes`
- `DeployPlugin`
- `UpdateEngine`
- `GetStatus` / `GetLogs`

The engine acknowledges receipt, executes, and streams progress events and final results back.

### 8.2 Monitoring
The Cloud dashboard displays:

- Real‑time equity, balance, drawdown, and margin for live sessions.
- Open positions and pending orders.
- Engine health: connectivity, last tick age, CPU/memory usage.
- Operation progress: backtest percent complete, optimisation generation and best fitness.

### 8.3 Reporting
All result data (trade histories, equity curves, population snapshots, per‑symbol metrics, correlation matrices) is stored in the Cloud. Users can generate reports (Excel, JSON, PDF) on demand, or configure periodic report generation. The engine never generates formatted reports; it streams raw data only.
